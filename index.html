Princípios de Engenharia

[ 02.A ]
Feedback
é inegociável
"Nunca deixar o cliente sem resposta. Nunca dizer que não vai dar — encontrar o caminho."

15 anos a lidar com clientes ensinaram-me que o silêncio é sempre a pior resposta. Quando um sistema falha sem dizer porquê, quando uma API retorna 500 sem contexto, quando o utilizador clica e não acontece nada — isso é um bug de comunicação antes de ser um bug de código. O sistema tem a obrigação de responder, sempre. Graceful degradation não é uma feature opcional; é o contrato mínimo com quem usa o que construímos.

nunca falha silenciosa · timeout sem feedback · estado indefinido
sempre mensagem de erro útil · fallback explícito · estado comunicado
padrão graceful degradation · circuit breaker · logging estruturado
[ 02.B ]
Problema
antes de código
"Primeiro ponho-me no lugar de quem tem o problema. Depois papel. Depois código."

O editor abre por último. Antes de escrever uma linha, preciso de perceber exactamente o que dói — não o que o cliente descreveu, mas o problema real que está por trás do pedido. Operações B2B ensinaram-me que o que é pedido e o que é necessário raramente são a mesma coisa. Em engenharia isso traduz-se em: mapear o domínio antes de modelar, entender o fluxo antes de criar o endpoint, questionar o requisito antes de o implementar.

sequência empatia → mapeamento → papel → código
ferramenta domain modelling · event storming · diagrama antes de IDE
alerta implementar o pedido literal sem questionar o porquê
[ 02.C ]
Verificar
antes de agir
"Um ataque man-in-the-middle num pagamento ensinou-me a nunca assumir que o canal é seguro."

A lição mais cara que aprendi não foi técnica — foi operacional. Um pagamento intercetado, dinheiro desviado, horas de gestão de crise. Recuperei, mas nunca esqueci. Desde então: verifico múltiplas vezes antes de qualquer acção irreversível. Em engenharia isso significa: validar inputs nas fronteiras do sistema, nunca confiar em dados não verificados, tratar toda a entrada externa como hostil até prova em contrário. Zero trust não é paranoia — é disciplina.

premissa toda a entrada externa é potencialmente hostil
padrão validação na fronteira · zero trust · confirmação antes de irreversível
aplica-se APIs · pagamentos · autenticação · migrações de dados
